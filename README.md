# vcompresor

An archiver that **unpacks compressed formats instead of swallowing them**, and gives your files
back byte for byte.

Made by [Vértice Labs](https://verticelabs.es/vcompresor) (León, Spain). *[Leer en español](README.es.md).*

A normal archiver sees a PNG, a `.docx` or a `.zip` as opaque bytes and can do nothing with
them: they arrive already compressed. vcompresor **unfolds** them (it undoes the DEFLATE, it
undoes the JPEG), compresses what is inside with its own context model, and on extraction
**rebuilds them exactly as they were**, byte for byte. That is where the big difference is, and
classic archivers cannot reach it without implementing the same thing.

```
900 source files, compressed inside a zip -9 of 2,130,467 bytes:

  vcompresor          854,908     <- unfolds the zip and models what is inside
  zstd -19          1,959,852
  xz -9             1,977,492
  the original zip  2,130,467

and gives back THE SAME ZIP, byte for byte.
```

## Three properties, in order of importance

**1. Reversible recompression.** DEFLATE (PNG, gzip, ZIP and everything that ships as a zip:
docx, xlsx, pptx, jar, apk, epub…) and JPEG (own parser: baseline and progressive). A stream
that cannot be unfolded is stored literally and does not drag down the rest of the file. The
reconstruction is **verified at compression time**: if it does not come out byte-identical, that
file is stored as is. Correctness is never traded for ratio.

**2. Byte-identical output on any architecture.** There is not a single floating-point
operation in the probability path. Compressing the same data on x86 and on ARM gives the same
SHA-256, and each one decompresses the other's output. For verifiable archiving,
content-addressed storage or regulatory compliance, that is not a detail. paq8px and cmix do
not have it.

**3. It mounts.** `vcompresor mount archive.vc /point` and you browse inside without unpacking.

Underneath: content-defined deduplication (variable-size chunking + blake3), reordering files by
similarity before packing, a lane that extracts the header timestamp from logs and stores it as
differences, three match models (two sequential and one strided, for record-structured data),
an x86 filter for executables, and parallel extraction.

## The numbers

Two comparisons, and both matter for different reasons:

- **zpaq -m5** is the rival in our *category*: it takes directory trees, deduplicates, and is a
  real product. It is the one to beat to claim "better archiver".
- **paq8px -8** is the *ratio* ceiling. It eats a single file, runs 39× slower and uses 2.4 GB.
  It is the one to measure against to know how far there is to go.

Both measured on this machine, not copied from any published table.

### 10 MB samples: here our archiver advantages are worth ZERO

No cross-file deduplication, no similarity reordering, no recompression lanes. It is just model
against model, and it is the ground that treats us worst:

| sample | vcompresor `--max` | zpaq -m5 | | paq8px -8 | |
|---|---|---|---|---|---|
| source code | **787,470** | 869,317 | -9.4% | 661,228 | **+19.1%** |
| CSV/JSON | **540,431** | 666,592 | -18.9% | 465,439 | **+16.1%** |
| enwik8 | **2,088,907** | 2,187,162 | -4.5% | 1,865,161 | **+12.0%** |
| logs | **48,823** | 75,717 | -35.5% | 31,385 | **+55.6%** |
| SQL | **226,104** | 351,320 | -35.6% | 158,372 | **+42.8%** |
| **total** | **3,691,735** | 4,150,108 | **-11.0%** | 3,181,585 | **+16.0%** |

*Generated by `bench/readme.py` from `bench/historia.jsonl`, 2026-08-03.*

We beat zpaq on all five, and **paq8px beats us by 21.9%**. Note where: the gap is *larger*
where the data is *more predictable* (SQL and logs, +71%), which is not a lack of models but of
**calibration**: it chains nine SSE stages where we had one.

### Real corpora, trees of thousands of files

Here deduplication, reordering and the lanes do count. **zpaq -m5 measured on the same machine
and in the same run**:

| corpus | input | vcompresor `--max` | zpaq -m5 | |
|---|---|---|---|---|
| source code | 136,415,253 | **9,657,771** | 10,901,842 | −11.41% |
| logs | 262,120,432 | **3,233,152** | 3,716,176 | −13.00% |
| SQL | 157,277,338 | **8,205,349** | 8,981,541 | −8.64% |
| CSV/JSON | 117,435,995 | **1,618,499** | 1,828,613 | −11.49% |
| **total** | 673,249,018 | **22,714,771** | 25,428,172 | **−10.67%** |

And on **Silesia**, the public reference corpus (twelve standalone files with nothing repeated
between them, the ground where deduplication is worth nothing and only the model counts):

| tool | bytes | ratio |
|---|---|---|
| **vcompresor `--max`** | **39,809,371** | **18.78%** |
| zpaq -m5 | 39,865,426 | 18.81% |
| 7z -mx9 | 48,715,234 | 22.99% |
| xz -9 | 48,776,804 | 23.01% |

The margin there is narrow, and we say so: **0.14%**. Silesia is twelve standalone files, many
of them binary, exactly where our advantages do not apply. There is also a trade-off worth
stating: the last model pruning gains 0.15% on the real corpora and **loses 0.10% here**.

Verified by extracting the whole archive and comparing it with `diff -rq` against the original:
zero differences across 27,804 files of the real corpus and the 12 of Silesia, including
symlinks, permissions, timestamps and empty directories.

On the source-code corpus, against the rest of the field: 7z -mx9 12,920,611 · xz -9
13,416,612 · mkdwarfs -l9 13,428,952 · zstd -19 --long 14,028,962.

### Speed, measured

This table is not written by hand: **`bench/readme.py` generates it from
`bench/historia.jsonl`**, and what does not come out of the ledger is not published. A
hand-written public figure goes stale and nobody notices; it already happened twice.

| | bytes | seconds | |
|---|---|---|---|
| **vcompresor `--max`** | **9,053,556** | 740.8 | **5.6× slower than zpaq** |
| vcompresor, default | 13,843,167 | 22.4 | 6.0× **faster** than zpaq |
| zpaq 7.15 `-m5` | 10,901,842 | 133.3 | |

**We are 5.6 times slower than zpaq**, and that is recent: on 28-07 the same measurement gave
145.0 s against 132.8. On **01-08 the clock tripled** to buy 1.5% of bytes; it is measured and
explained in `docs/f4-velocidad-por-que-son-mas-rapidos.md`.

Memory: ~1.1 GB with `--max`.

## Who we do NOT beat

This matters as much as the above.

- **paq8px beats us by 21.9%** on the 10 MB samples (table above). It is the king of
  deterministic context mixing and does it **without its neural network**: its LSTM is a
  separate option that `-8` does not enable. The price it pays: 0.008 MB/s and 2.4 GB of RAM,
  39× our time. And `-8` is not even its maximum: it goes up to `-12` with 29 GB.
  - Its advantage is **model capacity**, not resources: ~500 mixer inputs against our 33, an
    `IndirectModel` with 27 contexts against our 2, and a `DmcForest` of 10 models against our
    1. Checked: quadrupling our memory gives us 0.07%, and paq8px at `-4` (660 MB, half of ours)
    still beats us by 18.2% on source code.
- **Video and audio.** There is no lane for H.264, AAC or MP3. A specialised codec beats us.
- **`.rar` and `.7z`.** We do not unfold RAR or LZMA: they are stored as is with 0.01% overhead.
  If you are going to archive them, unpack them first.
- **The default mode** is very fast but compresses at zstd level, so it loses to 7z and xz.
  **The tables above are `--max` only.**
- **It does not shrink what is already compressed.** On video, JPEG or a `.zip` the archive will
  be *slightly larger* than the input: the floor is 118 B plus ~25 B per file, and on
  incompressible data it never goes below 100%. That happens to every archiver; here at least it
  is reported on screen when it occurs.
- **It does not write to the cloud.** Local disk only. restic and borg talk to S3 and SFTP; here
  uploading the file is up to you.
- **`mount` is Linux only** (it needs FUSE) and **the graphical app is macOS only**.

## Check it yourself

```bash
bash bench/run.sh
```

It downloads the public corpus from its original source, builds, measures vcompresor and the
rivals **on the same machine and in the same run**, and checks every round trip with
`diff -rq` against the original, not with a hash we give ourselves. If something fails, the
table says so.

## Usage

```
vcompresor compress <input>... -o backup.vc        # store
vcompresor list     backup.vc                      # see what is inside
vcompresor extract  backup.vc -o dir               # get everything back
vcompresor extract  backup.vc -o dir --file "*.pdf"  # get only that back
vcompresor add      backup.vc <input>...           # another snapshot
vcompresor forget   backup.vc <snapshot>           # delete it and compact
vcompresor verify   backup.vc                      # check without extracting
vcompresor mount    backup.vc <point>              # browse inside (Linux only)
```

`<input>` can be repeated: `compress a.mp4 b.mp4 notes/ -o backup.vc` stores those three things
and nothing else, with paths hanging from the folder that contains all of them. A single folder
stores its contents, as always.

The Spanish command names (`comprimir`, `descomprimir`, `añadir`…) still work as aliases.

`--max` uses the in-house context model instead of zstd: it compresses much more and is much
slower. It is the mode the tables above were measured with.

**If you do not know which one suits you, say it in money and it chooses:**

```
vcompresor compress /data -o backup.vc --price 5.55 --retention 36
```

It probes **your** data, prices each setting (the disk plus the CPU to get there) and uses the
cheapest, showing the whole table. Measured: at S3 prices level 19 pays off; at Backblaze prices
level 17; on cheap own disk level 9, and there level 19 **loses** money.

Other options: `--exclude PATTERN` (repeatable) to skip `node_modules` and friends, and
`--solid` for large frames on very repetitive data.

### Snapshots

`add` stores another copy of the same tree reusing everything that did not change. On 403 MiB,
the second copy of an identical tree adds **−24 B** (restic +821, borg +1,268), and with
realistic churn (insertions, appends, new files) we add **4.23× less than restic**.

`forget` deletes a snapshot **and compacts**: in the test it freed 98.8% of the archive. Without
that there is no possible retention policy and the archive grows forever.

### Encryption

```
vcompresor compress /data -o backup.vc --encrypt
```

ChaCha20-Poly1305 with a key derived by Argon2id. Both the frames **and the index** are
encrypted: the index holds the paths of every file, and a backup that leaks the directory tree
is not really encrypted.

The password is asked for on the terminal (no echo, and twice when creating), or taken from
`--password-file` or `VC_PASSWORD`. **Never as a command-line argument**: it would be visible in
`ps` to any user on the machine and would stay in the shell history.

Without that password there is no way to recover anything. **There is no recovery, by design.**

### Graphical app (macOS)

`app-macos/` holds a native app: drag a folder (or several loose files, and it stores those and
not the folder that contains them) or open a `.vc` and see what is inside, with a search box to
recover one or several files. The progress bar goes by bytes, not by file count.
`bash app-macos/empaqueta.sh` builds it. It is signed *ad hoc*: distributing it to third parties
would need an Apple developer account and notarisation.

### What it preserves

Permissions, timestamps, symlinks, **hard links** (they share an inode on restore), **sparse
files** (they stay sparse instead of inflating), **owner and group**, fifos and devices, and
**extended attributes**: on macOS that is where the Finder comment and colour tags live; on
Linux, SELinux labels and executable capabilities.

## Format and compatibility

`VCMP0016`. Every earlier format back to `VCMP0012` is readable, and that is verified on every
change by building the *previous* binary separately to produce a genuinely old archive.
Archives already written keep opening: it is a promise, not an intention.

## Status

R&D project. Round trips are verified at every step (own fuzzer, real corpora, `diff -rq`), but
it has not yet been through years of other people's use. If you are going to trust it with data
you do not have anywhere else, do not do it yet.

Dependencies: minimal, on purpose. No serde, no clap, no walkdir, no fastcdc. We keep blake3 (a
home-made safety net that failed subtly would certify a broken round trip as good), zstd, and
libjxl/preflate for the recompression lanes.

Technical notes for each step, with the measurements and **the experiments that did not
work**, are in [`docs/`](docs/) (in Spanish).

Binaries for Linux x86-64 and macOS (Apple Silicon) are in
[Releases](https://github.com/cristian-wpo/vcompresor/releases).
